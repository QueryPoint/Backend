# Отчёт нагрузочного тестирования (QA-04)

## Условия прогона

- Инструмент: Locust (`tests/load/locustfile.py`).
- Стенд: локальный docker-compose (Postgres, Redis, Elasticsearch, MinIO, RabbitMQ) + backend локально против него, база предварительно заполнена 10 документами через `Infra/init.sh`.
- Параметры: 50 одновременных пользователей (`-u 50`), скорость подключения 5 пользователей/с (`-r 5`), длительность 2 минуты (`-t 2m`).
- Команда:
  ```bash
  QA_LOAD_USERNAME=init_seed_user QA_LOAD_PASSWORD=init_seed_pass_123 QA_LOAD_QUERY="learning" \
  uv run locust -f tests/load/locustfile.py --host http://localhost:8000 --headless -u 50 -r 5 -t 2m \
    --csv=tests/load/reports/load_report --html=tests/load/reports/load_report.html
  ```
- Дата прогона: 06.07.2026. Сырые данные — `tests/load/reports/load_report_stats.csv`, `load_report_stats_history.csv`, полный HTML-отчёт — `tests/load/reports/load_report.html`.

## Наблюдения

1. **0% ошибок** на всём прогоне — backend не деградирует под нагрузкой 50 одновременных пользователей.
2. Поиск (основной сценарий, вес 4:1 к пустым результатам) отвечает за 13мс медианно — Redis-кеш (TTL 5 мин) заметно помогает, т.к. Locust-пользователи повторяют один и тот же запрос (`QA_LOAD_QUERY`).
3. `POST /login` заметно медленнее (медиана 350мс, p99 1900мс) — ожидаемо, т.к. bcrypt-хеширование пароля рассчитано быть медленным намеренно (защита от брутфорса), и все 50 пользователей логинятся практически одновременно в начале прогона (`on_start`), создавая кратковременный всплеск нагрузки на этот единственный эндпоинт.
4. Максимальное время ответа (~1.6-1.9с) — это выбросы в момент одновременного логина/старта всех пользователей, не устойчивая деградация (медиана и p90 остаются низкими).

## Итог

Backend выдерживает целевую нагрузку в 50 одновременных пользователей без единой ошибки, с медианным временем ответа поиска 13мс. Единственная точка внимания — стоимость bcrypt при массовом одновременном логине, что является осознанным компромиссом безопасности, а не дефектом.
